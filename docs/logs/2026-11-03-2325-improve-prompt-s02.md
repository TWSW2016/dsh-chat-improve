## 决策

- 保留第 1 条示例的"事实密度"（项目名、分支、保留项、完成标准），只去掉"怎么做"：既保住用户确认有效的"细节更多、更准确"，又不示范方案。
- 第 3 条示例放在最后：模型对末尾示例的模仿最强，正好压在失败样例上。
- 没有把三条示例统一成英文：语言跟随草稿是既有契约，中英各留一条能同时约束两种输出语言。
- 断言"每条示例都有完成判据"而不是只数示例条数：这是用户要求保留的四要素之一，防止后续改示例时悄悄丢掉。

## 问题与限制

- 示例 1 变短后，模型可能连带少写"简报里能推出的细节"；本轮没有真实模型输出可对照，需在步骤 4 之后用真实路由或 GUI 抽样确认。规则 2 已保留"scope, constraints, or context that the draft or the facts imply"，作为对冲。
- 新增示例 3 只用一条真实草稿做样本，代表性有限；`Update the latest plugin` 是已知失败样例，优先覆盖它。
- 测试断言 `Done when|完成标准` 为 3，是把"示例必须带完成判据"变成硬约束；以后加第 4 条示例必须同时加判据，否则测试失败。

## 可复用经验

- few-shot 改动比规则改动更影响输出；评审"生成质量"类问题应先看示例再改规则。
- 示例里出现具体实现（读哪些文件、改哪个模块）等于在教模型写方案；示例只应示范"输出形态"，不应示范"实现路径"。
- 在 JS 单引号字符串里写 Windows 路径要写成 `E:\\Repos\\…`；用 node 渲染一次全文即可确认转义没丢。
