## 决策

- 验收文档如实写"未覆盖"而不是写"通过"：没有真实模型输出就不能声称改写质量已验证，这是本仓既有约定（引用闸门一行也这么记）。
- 不在本会话重启应用或起第二个 `dsh web`：会打断当前对话，且运行中的宿主加载的是旧 Host 代码，抽样结果不代表新契约。
- `lib/client.js` 不改：宿主半由 `package.json` 的 `"./src/index.js"` 指向源码，构建只产出客户端 bundle；重建是回归动作，不是本步必需产物。

## 问题与限制

- 真实模型抽样未做：新契约是否真的压住"计划/方案/步骤"只能等宿主重载后用真实草稿验证；单测只证明指令文本与拼接正确。
- README 第 10 行本身就是简报里会送给模型的文本（`README excerpt`），现在它与指令契约互相引用；以后改契约必须同时改 README，否则模型会从摘录里读到旧描述。这是已知耦合，不是遗漏。
- Desktop 与 Web GUI 共用同一份 `lib/client.js`，但宿主半需要重载才生效；两种界面都受同一限制。

## 可复用经验

- 契约文字在三处重复（`SYSTEM_PROMPT`、README、计划 §3.5），改一处必须同步三处；验收文档是第四处，用"未覆盖"行记录待验证状态，避免把"单测绿"说成"行为已验证"。
- 只改 host 文件时 `lib/client.js` 尺寸不变，可作为"没有误改客户端"的快速信号。
- 每步提交前跑 `git status` 确认只剩本步文件，能及时发现 `.research`、`lib/` 之类的构建产物混入。
